## How to keep this useful

Add an entry for a meaningful milestone, problem, decision, or change in direction.
Use the local date of the work. Start with what happened and why it mattered.
Explain enough technical detail to make the decision understandable, without
turning the entry into a commit dump.

Each entry should preserve:

- The problem and the reason for working on it.
- What changed, and the tradeoffs behind the approach.
- A real obstacle or surprise, including the eventual fix when known.
- Current status: implemented, tested, owner-reported, or still planned.
- Evidence links to versions, commits, test notes, or checked-in documentation.
- Open questions and useful angles for a future post.

Use [the entry template](TEMPLATE.md) as a starting point. Do not invent motives,
quotes, hours worked, adoption, performance gains, or user feedback. Keep secrets,
private host details, credentials, conversations, and unrelated client work out.
Technical observations and owner reports are different kinds of evidence; label
both. Keep the version under test explicit when it differs from the latest build.

Repository visibility and website publication are separate decisions. Keeping this
diary in Git does not authorize publishing it to the website. The owner approved
public repository visibility on 2026-11-07 while alpha testing continues; diary
files are consequently public source material, not published website articles.
